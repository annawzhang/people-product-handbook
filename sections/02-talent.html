总览 理想 字节 腾讯 TCL 附录

八维可解释人才评分 + AB

归属：字节跳动 · Seed 招聘数据 — 对应简历「AI 人才量化建模 / 招聘 AB」。详见 字节入口。

线索太多时先联系谁：可配置加权、维度贡献可解释、S+/S/A/B/C 分层跟进，用 NOT EXISTS 排他 AB 证明有效。

flowchart LR SYN[synth.generate] --> FEAT[scoring.features] CFG[config/scoring.toml] --> SCORE FEAT --> SCORE[scoring.score] SCORE --> TIER[S+/S/A/B/C] TIER --> SIM[experiment.simulate] SIM --> DB[(SQLite)] DB --> FUN[funnel_by_tier] DB --> AB[ab_result + z-test] DB --> IDX[index_benchmark] FUN & AB & IDX --> REP[report.render HTML]

2. API / 模块调用

调用作用关键输出
load_config()读 TOML 权重/阈值/分层dimensions, tiers
generate(n, seed)虚构候选人Candidate[]
features(c, cfg)八维 0–100 特征含地域四因子梯度
score(c, cfg)加权总分 + 贡献说明total, tier, reason, missing
simulate(people, cfg)跟进与事件写入 SQLitedb, scores
ab_result(db)两组回复率 + z/pcontrol / treatment
layers(db)纯对照/纯实验/混合人数mixed 被排除
index_benchmark(db)索引前后查询耗时before_ms / after_ms
python3 run.py一键出报告docs/index.html, scores.csv

八维（公开口径）

维度权重口径备注
赛道关联度最高档之一与目标赛道重合
导师网络 / 本地资源 / 内部连接高关系与转介绍

3. Follow-up

追问答法
为什么不用机器学习排序？业务要改得动、讲得清；先专家加权 + AB，再考虑学习排序。
混合样本为什么要扔掉？同一人进两组会污染因果；NOT EXISTS 三层隔离。
准确率数字如何解读？报告里是虚构数据上的识别提升（二元→梯度）；真实业务需重标定。
和招聘评分卡什么关系？人才评分管「线索池优先级」；招聘评分卡管「岗位匹配与面试」。

5. Best practices

  • 权重变更必须带一版 AB 或回溯校准，禁止「拍脑袋调参」。
  • 缺失值显式进 missing，不要默当 0 分。
  • 分层策略写进配置（S+ 优先建联…），产品和运营同一套语言。
  • 慢查询先 explain 再加覆盖索引；报告里保留 before/after。
  • 下一步增强：校准图 + Brier（可复用 People Stats Kit）。

6. Demo 路径

  1. 打开报告：看分层人数与示例卡片「主要得分来自…」。
  2. 讲清地域维度：二元标签 → 四因子梯度。
  3. AB 段：回复率变化 + 混合样本排除 + SQL 加速。
  4. 本地 python3 run.py 证明可复现。
